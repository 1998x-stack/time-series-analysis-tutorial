CHAPTER 27 / 28 · DEPLOYMENT & MLOPS

生产部署与 MLOps：让预测在线上持续可用

一个在 notebook 里表现良好的模型，上线后可能悄悄失效。这一章讲清从训练到服务的工程链路，以及为什么对时序预测而言，「部署」之后还有一半的工作。

机制图解 · 原生数学排版 · 可复现模拟 · 边界与诊断

一个模型在 notebook 里可以很漂亮：交叉验证的误差很小，插图也能直接放进汇报。但它一旦开始对真实未来做预测，评价标准就变了——不再是一次性的离线评估，而是每天、每周持续兑现的承诺。数据会变、映射会变、代码环境会变，模型于是慢慢老去。

这一章把“从训练到服务”的链路拆开：怎样把一个模型包成别人能调用的服务，怎样管理它的版本，怎样用残差诊断与时序验证的思路去监控它，以及什么时候该重训练、怎样安全地发布。核心观点只有一句：对时序预测而言，“部署”不是终点，而是监控与维护的起点。

01 · 最后一公里为何会走样

先厘清一个常见误解：离线效果好、上线就差，往往不是模型“训练得不够好”，而是训练与部署面对的数据分布不同。离线评估用的是历史切成的时间片；上线后，数据是持续新生成的，而平稳性在这里恰恰是最脆弱的假设——很多真实序列的均值、方差或季节性结构会随时间漂移。

02 · 最小可行部署：把模型包成一个 API

让别人用起来，最直接的方式是用一个 Web 框架把模型封装成 HTTP 接口。下面是一个最小骨架（FastAPI），它只负责“加载模型 → 校验输入 → 返回预测”。真实服务还需预热、超时、并发隔离与鉴权，但骨架能先把职责分开。

# model_serve.py — 最小预测服务骨架
import numpy as np
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel

app = FastAPI(title="Time Series Forecasting API")
MODEL = load_model("model.pkl")          # 启动时加载一次，避免每请求重载

class ForecastRequest(BaseModel):
    history: list[float]                 # 已知历史，至少需要模型的最小上下文
    steps: int = 14

@app.post("/predict")
def predict(req: ForecastRequest):
    if len(req.history) < MIN_CONTEXT:
        raise HTTPException(400, "history too short")
    y = np.asarray(req.history, dtype=float)
    point = MODEL.forecast(y, steps=req.steps)   # 返回点预测与区间
    return {"forecast": point.tolist()}

# 启动：uvicorn model_serve:app --host 0.0.0.0 --port 8000

这里有一个时序特有的坑：模型往往有一个最小历史长度（ARIMA 需要足够的滞后与差分，深度学习需要固定的上下文窗口）。接口必须显式校验，而不是把残缺输入喂给模型后再崩。另一个高频问题是冷启动：首次请求触发模型加载，P99 延迟会出现长尾，通常用预加载或预热请求解决。

03 · 容器化：把环境一起打包

“本地能跑、服务器跑不了”几乎总是依赖版本差异造成的。容器化把代码、依赖与运行时一起固化，让训练环境和推理环境尽量一致。一个最小 Dockerfile：

FROM python:3.11-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt   # 版本在 requirements 中行锁定
COPY model.pkl model_serve.py ./
EXPOSE 8000
CMD ["uvicorn", "model_serve:app", "--host", "0.0.0.0", "--port", "8000"]

注意 requirements.txt 应锁定版本：时序库（statsmodels、numpy 等）在大版本间可能出现行为变化，不锁定会让“同样的代码”在不同时间构建出不同结果。容器化的收益（环境一致、可版本化、可弹性伸缩）也伴随着成本：镜像越大启动越慢，模型文件通常应放在外部存储而非烘进镜像。

04 · 版本与实验追踪：回答“线上跑的是哪个”

时序模型往往需要定期重训（每天/每周），每次都会产生一个新版本。没有版本管理，很快会出现两个无法回答的问题：线上到底跑的是哪个？上周效果更好的那个配置是什么？

这类工具（如 MLflow）通常提供三块能力：实验追踪（记录参数、指标与产物）、模型注册（管理版本与阶段，如 Staging / Production / Archived）、服务（把注册的模型部署为接口）。使用时关键不是工具本身，而是记全什么：

  • 数据窗口：训练用了哪段时间、怎样切分、随机种子是多少；
  • 超参：ARIMA 阶数、季节周期、树模型深度等；
  • 指标：不只 MAE/RMSE，还要 MASE（跨序列可比的相对误差，见 第 14 章）；
  • 残差诊断：残差的 Ljung-Box 检验 p 值。
为什么额外记残差诊断：误差指标小不等于模型没漏掉结构。若 MAE 看着不错，但残差仍明显自相关，说明模型没有充分利用时序信息；这个信号在重训时比单一误差值更有指导意义。

05 · 数据漂移与概念漂移

分布会变，但“变的是哪一部分”决定了监控手段不同，需要分开：

类型改变了什么典型场景常见信号
数据漂移
data drift		输入分布 P(X)用户结构、渠道或采集口径变化，特征分布整体平移特征统计量（均值/方差/分位数）与训练时不一致
概念漂移
concept drift		输入到输出的映射 P(Y|X)同样的促销力度，过往带动大幅增长，后来因用户疲劳效果变小输入没变但预测误差系统性地偏向一侧

时序场景里两者常同时发生，而且概念漂移更难对付：真值只在预测兑现之后才能观测到，因此误差信号总是滞后到账。这也意味着“残差监控”往往是能拿到的最早信号，下一节展开。

06 · 残差监控：最早能拿到的漂移信号

预测兑现后就能算残差 et=yt−y^t。如果模型是对的，残差应围绕 0 波动、且大体无自相关（见 第 4 章）。于是可以用一个滑窗均值检验残差是否系统性偏了一边：

zt=e‾ts/n,e‾t=1n∑i=t−n+1tei
ēt 为最近 n 个残差的均值，s 为其样本标准差。若模型无偏且残差近似独立，zt 近似服从标准正态，|z| 明显偏大就提示系统性偏差。这只是监控的启发式阈值，不代表严格检验。

除了均值偏移，还要看方差是否变大：一段时期内残差波动突然变宽，往往说明输入分布不稳。两种信号画在一起就是下面这张图：

07 · 自动重训练与安全发布

检测到漂移后，需要一条自动化的重训练流程。一个典型流水线：

  1. 定时拉取新数据（每小时/每天）；
  2. 校验新数据的完整性与质量（缺失率、异常值、单位）；
  3. 用滚动或扩展窗口重训练（窗口策略见 第 22 章）；
  4. 在同一套时间序列验证上对比新旧模型；
  5. 只有新模型显著更优（或旧模型已漂移）时才提升到 Production；
  6. 用蓝绿或金丝雀方式切换流量，并保留回滚点。
关键原则：重训练不是越频繁越好。对统计模型（ARIMA、ETS）而言，每次重训都要重新搜索超参，数据变化不大时新超参反而可能带来不稳定。稳妥做法是定期重训（如每周）加漂移触发重训，两者并行；且任何新版本都必须先经过与旧版本相同的时序验证。

发布方式上，蓝绿部署维护两套环境、验证后一次性切流，回滚就是切回去；金丝雀发布先让新版承担一小部分流量，观察一段时间再逐步扩大。两者共同的前提是可回滚：在 Model Registry 里把上一个可用版本标清楚，出问题时能快速恢复。

08 · 时序数据库与实时流

当预测系统需要处理高频数据流（如每秒接入的传感器读数），关系型数据库按行存储、缺乏时间窗口聚合能力就会成为瓶颈。这时会用到时序数据库（TSDB）与流处理框架：

工具类型典型定位特点
InfluxDB时序数据库IoT 监控、运维指标面向时间戳存储，写入吞吐高，支持降采样与保留策略
TimescaleDB时序数据库需与关系数据关联的场景基于 PostgreSQL，可用完整 SQL 与已有生态
Kafka流处理平台实时数据管道的中间层高吞吐、可持久化、支持重复消费
Flink流计算引擎实时特征计算与预测有状态计算、支持事件时间与水位线

一个常见组合是传感器 → Kafka → Flink（特征计算）→ 模型服务（推理）→ TSDB（结果与监控）。每一层职责单一，可以独立扩缩容。需要提醒的是，引入流处理会明显提高系统复杂度：如果预测频率只是每天一次，定时批处理通常已经够用，不必为了“实时”而过度设计。

09 · 生产就绪清单

把模型推到生产前，建议对照下面这份清单逐项确认。具体阈值（延迟、吞吐）应由业务 SLA 决定，而不是套用固定数字：

类别检查项说明
性能推理延迟满足 SLA关注 P99 而非均值，冷启动长尾尤其要看
性能吞吐量经过压测能承受预期峰值流量并留有余量
可靠性模型加载有预热避免部署更新时的首次请求延迟
可靠性降级方案已定义模型不可用时回退到 seasonal-naive 等简单 baseline
监控残差统计实时计算每批预测兑现后自动更新残差均值/方差
监控漂移告警已配置残差规则或 PSI/KS 等分布对比
运维模型版本可回滚Registry 中旧版本随时可取回
运维重训练流水线就绪定期与漂移触发两种方式并行
安全API 鉴权与限流预测接口不应对公网裸开
安全输入校验严格拒绝历史长度不足、含 NaN 等异常输入

10 · Python 实验：残差监控的均值统计量

下面用 numpy 模拟一段平稳残差，再人为注入均值漂移，验证上一节的 z 统计量能否区分两种情形。固定随机种子，只依赖 numpy。

import numpy as np
rng = np.random.default_rng(2701)

def residual_z(e, n=100):
    """最近 n 个残差均值的标准化统计量（假定残差近似独立）"""
    w = e[-n:]
    return w.mean() / (w.std(ddof=1) / np.sqrt(n))

e0 = rng.normal(0.0, 1.0, 1000)          # 平稳、无偏的残差
e1 = e0.copy()
e1[-120:] += 0.6                         # 最后 120 点注入均值漂移

print("无漂移 z =", round(residual_z(e0), 3))   # ≈ 0.357
print("有漂移 z =", round(residual_z(e1), 3))   # ≈ 6.339

assert abs(residual_z(e0)) < 2.0         # 平稳时不应报警
assert residual_z(e1) > 3.0             # 漂移时明显超阈

预期结果：无漂移时 z≈0.36，有漂移时 z≈6.34，两条断言均通过。这是对监控统计量语义的数值验证，不代表任何真实生产系统的误报率；真实阈值需用历史数据回测校准。

11 · 小结

这一章把“部署”扩成了一个闭环：服务化与容器化让模型可被调用且环境可复现；版本与实验追踪让每个预测都有出处；残差监控提供最早的漂移信号；自动重训练与安全发布让模型能持续更新而不失控。核心一句：“上线”不是终点，而是监控与维护的起点。

上线前请再问自己：线上到底跑的是哪个版本？残差在实时被监控吗？检测到漂移后，是自动重训还是人工介入？新版本能不能一键回滚？
